# 坐标系与位置核对

面板的位置显示、导航链接和距离排序都依赖坐标系。这份记录说明为什么 `stations_yuquan.csv` 里存的是 BD-09、哪里必须换算，以及结论是怎么核出来的。

## 结论

- 尼普顿接口 `obj.longitude` / `obj.latitude` 是 **BD-09（百度坐标系）**，不是 GCJ-02。
- `stations_yuquan.csv` 的 `lon,lat` 与上游设备坐标一致（见下），所以同样是 **BD-09**；存储保持原生值，方便随时与上游比对。
- 换算只发生在使用的时候：

| 用途 | 需要的坐标系 | 做法 |
| --- | --- | --- |
| 高德导航链接 | GCJ-02 | `bd09ToGcj02()` 后再传 `coordinate=gaode` |
| 百度导航链接 | BD-09 | 直接用，`coord_type=bd09ll` |
| 浏览器定位结果 | 返回 WGS-84 | `wgs84ToBd09()` 换算后再与站点比距离 |
| 设备位置告警（距本站多远） | 站点与设备同为 BD-09 | 直接比较，无需换算 |

换算函数集中在 `static/index.html` 顶部：`wgs84ToGcj02` / `gcj02ToBd09` / `bd09ToGcj02` / `wgs84ToBd09`。

## 问题是怎么暴露的

v1.0 的代码把接口坐标当成 GCJ-02 直接交给高德：

```js
/* v1.0：注释写的是「接口坐标与高德一致（GCJ-02）」——这个前提是错的 */
const amap = `...?to=${station.lon},${station.lat},...&coordinate=gaode...`;
```

BD-09 与 GCJ-02 在杭州相差约 **930 米**（经度约 +0.0065°、纬度约 +0.0060°），所以导航会落到隔壁街区，看起来「完全不是站点位置」。

## 判定依据

OSM（OpenStreetMap）数据是 WGS-84，与接口无关，可作独立参照。取 8 座名称明确的玉泉建筑，把 CSV 坐标按三种假设分别与同名建筑比对，看哪种残差最小：

| 站点 ↔ OSM 同名建筑 | A：CSV 是 WGS-84 | B：CSV 是 GCJ-02（v1.0 假设） | C：CSV 是 BD-09 |
| --- | --- | --- | --- |
| 教三北侧 ↔ 第三教学大楼 | 1176 m | 959 m | **32 m** |
| 教七北侧 ↔ 第七教学大楼 | 1197 m | 968 m | **29 m** |
| 教十（内部） ↔ 第十教学大楼 | 1150 m | 926 m | **21 m** |
| 曹光彪楼南侧 ↔ 曹光彪高科技大楼 | 1162 m | 912 m | **49 m** |
| 高分子系北侧 ↔ 高分子楼 | 1234 m | 1011 m | **72 m** |
| 电机楼南侧 ↔ 电机工程楼 | 1163 m | 912 m | **51 m** |
| 行政楼北侧 ↔ 行政楼 | 1176 m | 955 m | **24 m** |
| 新桥门南侧 ↔ 新桥门 | 1098 m | 859 m | **79 m** |
| **平均残差** | 1169 m | 938 m | **45 m** |

只有假设 C 的残差落在「建筑中心到站点实际位置」的正常范围内（建筑是有尺寸的，站点通常在楼侧或楼前），故判定 CSV/接口坐标为 BD-09。

> 注意：不能用「离最近的 OSM 要素有多远」来判断——校区内要素密集，任何错位都能在 50 米内找到某个要素，判断不出来。必须用**同名建筑**配对看残差。

## 站点坐标与上游的逐站核对

2026-09-18 用接口实时数据逐站比对（CSV ↔ 该站设备坐标中位数）：

- **12 个站点偏差 0–60 米**，属于同一栋楼的范围，`stations_yuquan.csv` 无需修改。
- 有上游登记问题的站点：

| 站点 | 情况 | 处理 |
| --- | --- | --- |
| 玉泉新桥门南侧 | 设备 `60359102` 上游登记为「浙大紫金港西区留学生宿舍wd12」（离本站约 5.8 km），另两台与本站相符（18 m / 22 m） | 站点坐标不动（已用 OSM「新桥门」验证，残差 79 m）；`60359102` 已从清单移除，不再计入玉泉站点的空位数 |
| 玉泉教七北侧 | 设备 `51059127` 偏离约 977 m，另两台相符（0 m / 8 m） | CSV 不动，由面板告警提示 |
| 玉泉生仪楼南侧 | 两台设备 `50559148` / `50559150` 彼此相差约 260 m，且都离 CSV 500–800 m | 保留 CSV：它的落点在教十 / 周亦卿科技大楼一带（37–59 m），而两台设备的落点在玉泉山、民宿那边（已在教学区外），因此设备坐标不可信 |
| 玉泉生仪楼南侧 | 设备 `50559147` / `50559149` 上游根本没登记坐标（接口返回空值） | 面板不显示其位置，也不作告警 |

设备级位置偏差一律由面板提示（`FAR_DEVICE_METERS = 300`），不改站点坐标——站点位置用于导航，不能被个别设备的漂移值带跑。

设备**归属**则按上游登记校对：`60359102` 上游登记为紫金港设备，已从 `stations_yuquan.csv` 移除（玉泉面板只统计玉泉设备，移除后该站从 3 台设备/36 孔变为 2 台设备/24 孔）。

## 复现方式

1. 拉取校区内 OSM 命名要素（WGS-84）：

```overpassql
[out:json][timeout:60];
(way["name"](30.255,120.108,30.282,120.138);
 node["name"](30.255,120.108,30.282,120.138););
out center tags;
```

2. 用同名建筑做配对，分别按三种假设算残差，取最小者。
3. 换算实现已做交叉验证：浏览器端 JS 与 Python 独立实现逐站比对，14 个站点坐标误差均为 **0.0000 m**。

## 改动导航相关代码时的注意事项

- 不要把 BD-09 直接传给高德（`coordinate=gaode` 会被当成 GCJ-02，偏约 930 米）。
- 不要对百度链接再做一次 GCJ→BD 转换（v1.0 犯过这个错，等于偏移两次）。
- 浏览器 `navigator.geolocation` 返回的是 WGS-84，量距前必须先换算，否则「按距离排序」最多会错 1 公里以上。
- 站点与设备的距离告警不需要换算（两者同为 BD-09）。
